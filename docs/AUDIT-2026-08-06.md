# Enterprise readiness audit

**Date:** 2026-08-06. **Scope:** the `legibility` app repo, the live deploy at
`https://legibility.io`, and Supabase `cgkcplcamsijghalintq`.
**Posture:** reviewed as an engineer at a large enterprise customer deciding whether to depend on
this service. That reviewer is not asking "is it clever", they are asking "what happens when it
breaks at 3am and who is accountable".

## Verdict

**Not 10/10. Roughly 6/10 as a technical product, 7/10 as a landing page, 8/10 on GEO and SEO.**

The engineering judgement on display is genuinely above average. The honest-scope documentation,
the trusted-read billing unit, the calibration gate, the fail-closed entitlement check and the
llms.txt are all things most teams do not do. The gaps are not sophistication gaps. They are
discipline gaps, and they are the exact ones an enterprise reviewer opens with.

The single sentence that ends most enterprise reviews: **there is not one automated test in this
repository.**

---

## What I could not verify, stated first

Per the working rule that access failures are reported before conclusions, not after.

- **`bun install` could not complete in this environment.** Repeated attempts dropped tarballs
  with `ConnectionClosed`. Every local `tsc --noEmit` run therefore reported
  `TS2307: Cannot find module` for `@supabase/supabase-js` and `zod`. Those are environment
  artifacts, **not** findings about the code. **Typecheck remains unverified.**
- **Playwright could not reach the live site** through this environment's proxy
  (`ERR_CONNECTION_RESET`). No rendered-browser visual QA, no automated axe accessibility scan,
  no Lighthouse. Accessibility findings below come from static analysis of the served HTML, which
  catches structural issues but not contrast, focus order, or keyboard traps.
- The **worker repo** (`plinth-worker`) is not in this session. Everything about extraction,
  calibration and `legibility_id` minting is out of scope here.

## 1. Testing and verification: the blocking gap

| Check | State |
|---|---|
| Test files | **Zero.** No `*.test.*`, no `*.spec.*`, no `vitest.config` |
| Test framework | **None** in `package.json` |
| `test` script | **Does not exist** |
| CI test job | **Does not exist** |

Four REST tools, an MCP JSON-RPC server, a hand-rolled Stripe webhook signature verifier with
`timingSafeEqual` and a 300 second replay window, an x402 payment flow, a billing gate, and a
metering path that decides what a customer is charged. None of it has a single test.

The Stripe webhook verifier is the sharpest example. It is hand-rolled HMAC-SHA256 crypto that
decides whether a payment event is authentic. That is precisely the code that must have tests,
and it has none.

**This is the finding that matters most.** Everything else on this list is a day of work. This
one is a project.

### CI is weaker than it looks

`.github/workflows/ci.yml` has two jobs and four steps that matter:

- `gitleaks` secret scan. Good, and it covers full history.
- Em dash check. Covers `src/` only.
- `tsc --noEmit`. Real.
- `bun run lint` with **`continue-on-error: true`**. Non-blocking.
- `bun run build`. Real.

So "green CI" currently means "it compiles and has no em dashes in `src/`". It does not mean the
code works, because nothing checks that.

**And CI has never run on the rebrand.** The workflow triggers on `pull_request` and `push` to
`main`. The 74 changed files of the Plinth to Legibility rename sit on
`claude/new-session-f66hba`, which is neither. The only evidence the rebrand builds is that
Vercel deployed it and `legibility.io` serves correct HTML. That verifies the **build**. It does
not verify the **typecheck**, which is a separate CI step Vercel does not run.

**Recommendation:** open a PR from this branch so CI runs, and drop `continue-on-error` from the
lint step.

### Formatting debt

45 files fail `prettier --check`, producing 1023 eslint errors. I checked whether the rebrand
caused this by running prettier against the pre-rebrand `terms.tsx`: **it failed too.** The debt
predates the rename and is not rebrand damage. It is invisible today only because CI ignores
lint. `bun run format` fixes all of it mechanically.

## 2. Security

### Findings from the Supabase linter

| Level | Finding | Assessment |
|---|---|---|
| WARN | **Leaked password protection disabled** | Real, and a one-click fix in the Auth dashboard. Enable it. Enterprise security questionnaires ask this by name |
| WARN | `has_role()` is `SECURITY DEFINER` and callable by `authenticated` via `/rest/v1/rpc/has_role` | Standard Supabase pattern, but it lets any signed-in user probe role assignments. Revoke `EXECUTE` from `authenticated` |
| WARN | `usage_current_period()` same exposure | Lower risk: migration `20260620120000` hardened it to filter on `auth.uid()` internally. Confirm and document as intentional |
| INFO | RLS enabled, no policies on `golden_eval_runs`, `ops_alerts`, `ops_daily` | **Intentional and correct.** No policy means deny-all, which is right for service-role-only tables. Worth a comment in the migration so the next reviewer does not "fix" it |

### Findings from code review

- **Exposed keys still unrotated.** `docs/OUTSTANDING.md` records previously exposed Stripe
  `sk_live` keys and the Supabase service-role key as still valid. I confirmed no live secret is
  in any tracked file today, and gitleaks covers history. But believed-exposed-and-still-valid is
  the worst state. **Rotate them.** This is independent of all other work.
- **The Stripe webhook always returns 200, even on internal error.** Errors are `console.error`
  only. Stripe treats 200 as delivered and will not retry, so a transient Supabase failure
  silently loses a subscription or invoice event permanently. For a billing surface this is the
  most consequential correctness bug in the repo. Return a 5xx on internal failure so Stripe
  retries.
- **Metering is best-effort.** The `usage_events` insert sits inside a `try {} catch {}` that
  swallows failures so the response still succeeds. Defensible for availability, but it means
  billing can silently under-count with no alert. At minimum, emit an error metric on the catch.
- **`compare_products` meters once** for a call that fans out N worker requests, stamping the
  domain of the first URL only. Cost attribution is approximate by construction.

### Correct and worth crediting

- Keys are sha256-hashed at rest, shown once, with column-level grants excluding `key_hash` from
  `anon` and `authenticated`.
- `entitlement_check` returns 402 **before** the worker call, so the free tier is a genuine hard
  stop rather than an invoice surprise. Backed by a cost fuse.
- The worker call is fail-closed: missing env returns 503 rather than proceeding.
- `postOnly` / `getOnly` method guards on every route except `/api/mcp`, which hand-rolls its own.

## 3. Correctness bugs found

**`robots.txt` group inheritance is wrong.** The file sets:

```
User-agent: *
Allow: /
Disallow: /dashboard

User-agent: GPTBot
Allow: /
...
```

Per the robots exclusion protocol a crawler obeys **only the most specific matching group**, and
groups are not additive. Every named AI crawler (GPTBot, ClaudeBot, PerplexityBot, CCBot,
Bytespider and the rest) matches its own group, which has no `Disallow`. **All of them are
therefore permitted to crawl `/dashboard`.** Each named group needs its own
`Disallow: /dashboard` line.

The pages are auth-gated so nothing sensitive leaks, but it is a real defect in a file whose
entire purpose is instructing crawlers.

**`llms.txt` advertises products that do not exist.** It lists a **Custom** plan ("quote, for
250,000 or more reads per month, on-prem extractor and data residency") and attributes "higher
rate limits, Slack, SLA" to Growth. The live `plans` table contains exactly three rows: free,
starter, growth. There is no Custom plan, no Slack channel and no SLA. This file is written
specifically to be ingested and quoted by AI answer engines, so the overclaim propagates.

**`llms.txt` tells crawlers the domain may be dead.** It closes with a note that as of
2026-07-06 "DNS was still propagating" and instructs the reader to curl the domain and confirm it
200s "so agents are not sent to a dead or misconfigured domain". The domain is fully live. This
paragraph is a leftover, and it is the last thing an answer engine reads.

**`trust_rate_by_method` does not group by method.** Carried over from the Phase 0 report: it
groups by `split_part(domain, ':', 1)`, which is the hostname. `docs/KILL-CRITERIA.md` claims it
breaks out jsonld, shopify, barcode and opengraph. It does not.

## 4. Landing page

**Content is correct.** I fetched the live HTML and confirmed **zero** occurrences of any
`plinth` string. Title, meta description, OG and Twitter tags are all correctly rebranded.

**Structure is clean.** One `h1`, seven `h2`, no skipped levels, `lang="en"` present, both images
carry `alt`, 14 `aria-*` attributes in use.

**The copy is good.** The h1 does the job in two beats:

> Agents can decide what to buy.
> *Reading the product page is where they still break.*

That names the problem before naming the product, which is the right order.

### Issues

- **No skip link.** Nothing matching "skip to content" or an equivalent in the served HTML. This
  is **WCAG 2.4.1 Bypass Blocks, Level A**. It is the most commonly cited automated a11y failure
  in enterprise procurement and it is roughly six lines to fix.
- **TTFB of 1.55s** on the homepage, 1.58s total. For a static-content marketing page on Vercel
  that is slow, and it is the metric a reviewer screenshots.
- **`og.png` and `favicon.png` still carry the old brand.** The OG image reads "plinth." and
  "onplinth.io" and appears on every social share, Slack unfurl and LinkedIn preview. You have
  said you are handling branding assets, so this is listed for completeness only.
- **Contrast, focus order and keyboard navigation are unverified** because the browser could not
  reach the site from here. These need a real pass before any accessibility claim.

## 5. GEO and SEO

**This is the strongest part of the product, and it is close to the 11/10 you asked about.**

What is genuinely excellent:

- **`robots.txt` explicitly welcomes AI crawlers** by name rather than defensively blocking them.
  For an agent-native product that is exactly right and most companies get it backwards.
- **`llms.txt` is the best artifact in the repository.** It states honest scope, names the
  competitors (Diffbot, Firecrawl) and argues against them on specifics, and carries an explicit
  "Not built yet, do not attribute these to Legibility" section. That last section is rare and it
  is precisely what stops an answer engine hallucinating features you do not have.
- **`/.well-known/mcp.json`** for agent discovery, with auth methods and per-tool descriptions.
- **Sitemap is generated from the route tree on every build**, so it cannot drift.
- **JSON-LD** with `Offer` nodes for all three plans.
- All 13 public routes return 200.

What would move it from 8 to 11:

- Fix the two `llms.txt` defects above (phantom Custom plan, stale DNS paragraph). Right now the
  file's credibility is its whole value, and both defects attack exactly that.
- **No `lastmod` in the sitemap.** Cheap to add from git and it materially affects recrawl.
- **No `FAQPage` or `HowTo` JSON-LD.** For a product whose buyers ask "how do I authenticate",
  "what does confidence mean", "what happens on a null read", FAQ schema is the highest-leverage
  remaining GEO win. Answer engines quote it directly.
- **No `BreadcrumbList`** on the docs pages.
- **`mcp.json` lists a personal Gmail address as the contact.** For an enterprise buyer that
  single field undercuts everything else on the page. Use `support@legibility.io`.
- **`onplinth.io` returns `DEPLOYMENT_NOT_FOUND`.** Every bit of SEO and GEO authority accrued
  under the old name is currently orphaned. A 301 to `legibility.io` preserves it and takes two
  minutes in Vercel.

- `@modelcontextprotocol/sdk` and `mcp-tanstack-start` are dependencies but **imported nowhere**.

  absent entirely. Regenerate.
- The em dash rule covers `src/` only, and recurses into binary PNGs in `src/assets/` and the

- `resolutions`, `webhooks`, `webhook_deliveries`, `invoices` and `audit_log` are schema-complete
  and entirely unused. Fine as reserved surface, but they carry unused indexes the linter now

## 7. Performance (database)

All INFO or WARN, none urgent at current volume, all worth fixing before traffic arrives:

- `outcome_reports` has an **unindexed foreign key** (`user_id`).
- Both `outcome_reports` RLS policies **re-evaluate `auth.uid()` per row**. Wrap as
  `(select auth.uid())`. This is the standard Supabase scaling trap.
- Eight unused indexes. Expected at zero traffic; recheck after the panel runs.
- Auth uses an **absolute** connection limit of 10 rather than percentage-based, so scaling the
  instance will not scale auth.

## Deliberately not done, with reasons

- **`has_role` EXECUTE not revoked.** The linter flags it, but it is Supabase's documented RBAC
  pattern and the policies on `profiles` and `waitlist` evaluate it as the querying user, so
  revoking would break dashboard access. I tested the revoke inside a rolled-back transaction
  rather than guessing. Residual risk is minor: a signed-in user could probe whether a given id
  is an admin. Documented as intentional.
- **`types.ts` not regenerated.** It is stale (`product_cache` missing `field_confidence`,
  `calibration_version`, `legibility_id`; `ops_daily` and `ops_alerts` absent). The current
  generator emits a newer shape (`Args: never`, `__InternalSupabase`), and with `bun install`
  failing here I could not typecheck the result. Shipping an unverifiable change to the file every
  query is typed against is the wrong trade. It causes no live bug today because this repo never
  writes to `product_cache`. **Do it in a PR where CI can verify it.**
- **`bun run format` not run.** It would touch 45 files and bury the substantive changes above in
  a 1000-line formatting diff. Worth doing, but on its own commit.
- **Leaked password protection not enabled.** Auth dashboard setting, not reachable from here.
- **`mcp.json` Gmail contact not changed.** Swapping it for a `support@legibility.io` that does
  not yet receive mail would be worse than the current working address. Create the mailbox first.
- **Branding assets** (`og.png`, `favicon.png`) left to you as agreed.
